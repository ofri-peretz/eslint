fix: four adoption-scan false positives in browser-security and node-security, decided by what the file does with the value

Four rules stop reporting code that cannot do the harm they name, each decided by what the file does with the value, never by a name. `browser-security/no-innerhtml` no longer reports a write into an inert holder (a `<template>`, a `<style>`, or a `createHTMLDocument` / `DOMParser` document) whose every use only reads a string back out, a `const` that holds sanitiser output, or a local function that returns a sanitiser's output or rewrites all five of `& < > " '`; a template whose content reaches the page, a detached `div`, a branch that skips the sanitiser, and an escaper missing the quotes keep reporting (24 of 37 findings on Trilium, plus tldraw, element-web, hedgedoc). `browser-security/require-blob-url-revocation` now sees a revoke that goes through a `useState` setter, a collection that a loop or callback revokes, a function in the file that revokes its argument, an alias of a ref, or a `#private` field; a URL stored where nothing revokes it keeps reporting (tldraw, element-web, Trilium, start-ui-web). `browser-security/no-http-urls` no longer reports a string used only as the namespace argument of `getAttributeNS`, `createElementNS` and their siblings, so an unlisted authority such as `ns.google.com` is covered by position; a constant that is also fetched keeps reporting (element-web). `node-security/no-zip-slip` no longer reports `tar.extract` from node-tar called with an options literal that leaves `preservePaths` off, or a joined path that only becomes error or console text; `preservePaths: true`, options held in a variable and a path that also opens a file keep reporting (Budibase, oracle).
