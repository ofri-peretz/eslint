eslint-plugin-security is maintained (latest release 2026-10-30), so the usual alternative is a second tool next to it, not a swap: `eslint-plugin-no-unsanitized` for DOM sinks, `eslint-plugin-secure-coding` and `eslint-plugin-node-security` (both ours) for more Node and general rules, and Semgrep or CodeQL outside ESLint for cross-file analysis. This page compares them and ends with combinations, not a winner.

**Covers ESLint 9 and 10 (flat config). Dates are from the npm registry and the GitHub API, read on 2026-11-19. Last updated 2026-11-19.**

The smallest change keeps `eslint-plugin-security` and adds the DOM rules it lacks. On 2026-11-19 the two plugins reported different statements on a test file, with no line reported twice, on ESLint 9.39.4 and 10.15.0:

{/* VERIFY: run on ESLint 9 and 10 */}
```js title="eslint.config.js"
import security from 'eslint-plugin-security';
import noUnsanitized from 'eslint-plugin-no-unsanitized';

export default [
  security.configs.recommended,
  noUnsanitized.configs.recommended,
];
```

```bash
npm install --save-dev eslint-plugin-security eslint-plugin-no-unsanitized
```

To add ours as well, read [Security plugins in one flat config](/docs/getting-started/security-plugins-one-flat-config) first. Several of our rules and `eslint-plugin-security` rules report the same line.

## Notes on each tool

**eslint-plugin-security.** All 15 rules are in its `recommended` config at `warn`. Its README says the plugin finds many false positives that need human triage. `detect-object-injection` reports every `obj[key]` access it cannot prove safe; it reported `obj[key] = 1` in our test file. It reported none of the DOM sink statements we tried (see the link above). It declares no ESLint peer range, so a package manager will not warn you about an incompatible ESLint.

**eslint-plugin-no-unsanitized.** Two rules, both for DOM sinks. It is a Mozilla project with a narrow scope and is the neutral choice for that scope. It needs ESLint 9 or later. It accepts only `escapeHTML` tagged templates and `.setHTML()` by default, and DOMPurify must be listed in its options.

**eslint-plugin-n.** Not a security plugin; include it because it is often installed beside one. It does not replace any security rule above.

**eslint-plugin-secure-coding and eslint-plugin-node-security (ours).** More rule categories than `eslint-plugin-security`, with messages that carry a CWE. Costs: Node 22.13 or later, a faster release cadence, and several rules that report the same line as an `eslint-plugin-security` rule or as each other. Some of our rules attribute a value to a request before reporting, so they stay silent on a bare function parameter where `eslint-plugin-security` reports (measured on a 3-file fixture, 2026-11-19). `secure-coding` documents `no-disabled-template-escaping` and `no-invisible-characters` as drop-ins for `detect-disable-mustache-escape` and `detect-invisible-characters`, and has a `no-bidi-characters` rule for the topic of `detect-bidi-characters` (not compared line by line).

**Semgrep.** A standalone scanner for many languages. Its open-source Community Edition analyzes within a single function, and cross-function and cross-file analysis belong to Semgrep Code, per Semgrep's documentation. Its rules repository has JavaScript browser rules whose file names cover `innerHTML`, `eval`, insecure `document` methods, `postMessage` origins and open redirects. We did not run it for this page.

**CodeQL.** A standalone analyzer that builds a database of the code, then runs queries over it. The `github/codeql` repository has JavaScript queries for reflected, stored and DOM-based XSS under `javascript/ql/src/Security/CWE-079`. Its CLI is covered by the GitHub CodeQL Terms and Conditions unless you have a GitHub Enterprise license; read them before using it on private code. We did not run it for this page.

## What was measured, and what was not

One corpus run compares three of these. It was run 2026-11-15 on ESLint 10.14.0 over 45 CWEs, with 100 vulnerable and 96 safe samples. **We wrote the corpus**, so it shows what our rules were built for more than how often each tool is right on your code.

| Tool                                                      | Vulnerable found (of 100) | Safe flagged (of 96) |
| :-------------------------------------------------------- | ------------------------: | -------------------: |
| eslint-plugin-security 4.2.1                              |                        15 |                   12 |
| eslint-plugin-no-unsanitized 4.1.5                        |                         4 |                    1 |
| Interlace: every one of our security plugins' `recommended` presets together |                        88 |                    0 |

The last row is not `secure-coding` plus `node-security`. Those two found 18 and 19 samples respectively (a sample can be counted by both); the rest came from our other plugins, listed on [Use alongside eslint-plugin-security](/docs/getting-started/with-eslint-plugin-security). `no-unsanitized` covers DOM sinks only, so a low count against a 45-CWE corpus says little about it. Our 0 of 96 does not carry over to real code: on 20 open-source projects (3.04M lines), 28.6% of Interlace's `recommended` findings and 13.0% of `eslint-plugin-security`'s were right, from 24 sampled findings per side. See [benchmarks](/docs/benchmarks).

A second run, on three vulnerable training apps and graded against their documented flaws, is on [eslint-plugin-security alternative: measured on NodeGoat, DVNA and Juice Shop](/docs/getting-started/security-alternative-benchmark).

Unmeasured, and so without numbers here: `eslint-plugin-n`, Semgrep and CodeQL on any corpus; the run time of any tool; false-positive rates of any tool on your repository. The comparison with CodeQL and Semgrep as categories is on [Interlace vs CodeQL vs Semgrep vs Snyk Code](/docs/getting-started/concepts/compare).

## Combinations

Pick by what you ship, not by a ranking.

- **Server code, already on `eslint-plugin-security`.** Keep it. Add `node-security` if you want the Node rules it lacks; accept or remove the duplicate reports as described in [one flat config](/docs/getting-started/security-plugins-one-flat-config).
- **Browser code.** `eslint-plugin-no-unsanitized` alone, or `eslint-plugin-browser-security` alone, or both with the duplicates removed. Neither follows a value across files.
- **Full-stack monorepo.** `eslint-plugin-security` on server globs, `no-unsanitized` or `browser-security` on client globs, scoped with `files`. The [one flat config](/docs/getting-started/security-plugins-one-flat-config) page has a tested file.
- **Injection and secrets beyond Node built-ins.** Add `secure-coding` (ours) to any of the above.
- **A value that crosses files or functions.** Add CodeQL, or Semgrep with its cross-file analysis, in CI. They run alongside ESLint; neither replaces the lint rules in your editor.
- **Node compatibility only.** `eslint-plugin-n`, with no security plugin implied.

A project with little Node built-in usage and no DOM code may reasonably stay on `eslint-plugin-security` alone.
