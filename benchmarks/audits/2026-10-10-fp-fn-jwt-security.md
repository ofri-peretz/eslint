# FP/FN audit: eslint-plugin-jwt-security (2026-10-10)

The source review ran against the published 3.3.0 (main was identical). Its findings are numbered FP-1…FP-13 and FN-1…FN-9. Some findings bundle two problems, so they are split into rows here, giving 29 items in total: **22 fixed** and **7 deferred**. One deferred item, the FP-4 residual, sits under a fixed row and is described in the deferred section.

**How the fixes were made: test-first.** Every new case went into the rule's existing test file under a `… — audit 2026-10` describe block. Run against the unchanged `src/utils` (restored from `HEAD` for the run), the suite showed `Tests 101 failed | 585 passed (686)`. After the fixes it shows `Tests 685 passed (685)` with 100/100/100/100 coverage.

**Design constraint (binding).** Every fix is AST-structural:

- **What is followed:** a same-file `const` binding (through the ESLint scope manager), `as` / `satisfies` casts, a spread of such a const, a `this.<member>` whose type annotation names an imported type, and the import binding of a callee.
- **What is not followed:** parameters, imports, calls, `let` / `var`. These are **opaque**, and a "missing option" rule is silent on an opaque value.

Litmus check: renaming every variable to `foo`/`bar` changes no verdict in the new tests. The one name-based heuristic left in the plugin (no-algorithm-confusion's `/public/i`) predates this audit. Its FP is deferred below.

**Recall locks.** Every fix also has invalid-side cases (each named "… keeps recall" or "… still reports"). They prove the rule still fires on the vulnerable shape after the FP fix. Examples:

- `FP-1 keeps recall: a const that lacks algorithms`
- `FP-5 keeps recall: destructuring an authority claim`
- `FP-6 keeps recall: header.alg without the option`
- `a jose builder held in a const with no expiry anywhere still reports`

**Existing tests changed** (each change is justified in a comment beside the test):

- **require-max-age:** `jwt.verify(token, secret, { clockTolerance: 30 })` moved from valid to invalid (FN-7). `clockTolerance` widens the expiry window, so accepting it as a max age certified a verify that caps nothing.
- **no-hardcoded-secret:** the inline `'-----BEGIN PUBLIC KEY-----…'` invalid case became `'-----BEGIN PRIVATE KEY-----…'`, which keeps the recall it was guarding. The public-key spelling moved to valid (FP-8).
- **no-decode-without-verify:** the corpus case `const { exp } = jwt.decode(token)` became `const { exp, sub } = …`. It had been reported only because destructuring was never followed, which was an implementation limit rather than a security judgement (FP-5).
- **coverage-dual-layer.test.ts:** the Layer-2 mock-context block covered the defensive guards inside `no-hardcoded-secret`'s private `resolveConstLiteralValue`. That function is deleted, so the block was removed with it.
- **utils.test.ts:** the `getOptionsArgument` cases were removed because the helper itself was removed. `resolveCallOptions` replaced it and is covered by the rule tests.

## Deferred items

| Item                                                                                              | Reason                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FP-4 residual: **untyped** injected receivers (`constructor(@Inject(X) private svc)`, a JS class) | There is no annotation to read, so the receiver can only be judged from its _name_, which the design constraint forbids. Typed members are fixed.                                                                                                                                                                                                                                                                                                              |
| FP-11 (b): `noTimestamp: true` reported by two rules                                              | The overlap is deliberate across presets. `no-timestamp-manipulation` is in `recommended`; `require-issued-at` is only in `strict`, where it reports the same call as the missing claim. Deduplicating means removing one rule's jsonwebtoken check, which is a preset-behaviour decision for the owner.                                                                                                                                                       |
| FP-12 (FP side): `PUBLIC_WIDGET_HMAC_SECRET` with `['HS256']` reported as confusion               | The HS-only branch of no-algorithm-confusion is a pre-existing **variable-name heuristic** (`/public/i`, `/publicKey/i`). It fails the rename litmus in both directions, and no structural fix exists for an HMAC-only list. The structural signal (mixed families) is now implemented and catches the real CVE shape whatever the key is named. Dropping the name patterns would flip existing invalid tests to valid, so that decision is left to the owner. |
| FN-3 (b): NestJS `sign(payload)` where the module sets no `expiresIn`                             | `JwtModule.register({ signOptions })` normally lives in a different file (`auth.module.ts`). Seeing it takes cross-file analysis. The rule now abstains on a one-argument `sign` on a plain receiver instead of guessing.                                                                                                                                                                                                                                      |
| FN-5 (b): unbounded `clockTolerance`                                                              | A numeric ceiling (300 s? 3600 s?) is a policy number, not a structural fact. It is better added as a rule option than hard-coded in an FP/FN fix.                                                                                                                                                                                                                                                                                                             |
| FN-6 (b): `jwt.sign({ ...user })` with `user` a parameter or a DB row                             | What the spread carries is only knowable by following the value (data flow) or from its type. The spread is marked opaque and the rule stays silent.                                                                                                                                                                                                                                                                                                           |
| FN-8: grant-response exemption depends on the receiver's _name_                                   | The exemption decides front-channel vs back-channel from `REQUEST_RECEIVER`, a name regex. Any fix that extends it (resolving `data` to `await request.json()`) is still name-based. A real fix needs provenance (is the value the body of a `fetch` to a token endpoint?), which is data flow.                                                                                                                                                                |

## Preset changes

**`recommended`, `strict` and `legacy`: no change.** No rule was added, removed or re-levelled.

Behaviour changes that reach users through the existing presets:

- `no-hardcoded-secret` and `no-weak-secret` now set `skipTestFiles: true`, matching `require-expiration` and `no-decode-without-verify`. A fixture token signed with `'test-secret'` inside a test ships no credential. `no-hardcoded-secret` is the one rule in `legacy`, so legacy users also stop seeing test-file findings.
- New findings can appear in the default presets:
  - `ignoreExpiration: true` (`no-timestamp-manipulation`, recommended)
  - mixed HS\*/asymmetric `algorithms` lists (`no-algorithm-confusion`, recommended)
  - `||` / `??` fallback secrets and config-object secrets (`no-hardcoded-secret` / `no-weak-secret`, recommended)
  - `clockTolerance`-only verifies (`require-max-age`, strict)
  - jose builders without `setIssuedAt()` (`require-issued-at`, strict)

  All are intended true positives. The changeset lists them under "Upgrade notes".
