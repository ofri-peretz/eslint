# FP/FN audit: eslint-plugin-jwt-security (2026-10-10)

The source review ran against the published 3.3.0 (main was identical). Its findings are numbered FP-1…FP-13 and FN-1…FN-9. Some findings bundle two problems, so they are split into rows here, giving 29 items in total (the FP-4 residual now has its own row). **All 29 are fixed.** The first pass (PR #1188) fixed 22 and deferred 7; the zero-deferral pass (2026-10-11, branch `fix/fp-fn-zero-deferred`) fixed those 7 under a design constraint the owner relaxed for it, and applied the owner's binding decisions on FP-11b, FP-12, FN-5b, the FP-4 residual, FN-3b, FN-6b and FN-8.

**How the fixes were made: test-first.** Every new case went into the rule's existing test file under a `… — audit 2026-10` describe block. First pass: run against the unchanged `src/utils`, the suite showed `Tests 101 failed | 585 passed (686)`; after the fixes, `Tests 685 passed (685)`. Zero-deferral pass: the new and flipped cases, run against `main` at f63163241, showed `Tests 53 failed | 704 passed (757)`; after the fixes the suite shows `Tests 813 passed (813)` with 100/100/100/100 coverage. Every `FP:` / `FN:` case carries a `// @found` note.

**Design constraint.** First pass: AST-structural only (same-file `const`, casts, spreads of a const, type annotations, import bindings). The zero-deferral pass ran under the owner's relaxed constraint:

- **(a) Intra-file value following** (`src/utils/value-flow.ts`): a `const`, or a `let` / `var` never reassigned; a destructure; a member of an object literal; a spread; an `await`; a cast; the single `return` of a same-file function. Bounded at depth 8 and guarded against cycles. What it cannot follow (a parameter, an import, an unreadable call) stays **opaque**, and a "missing option" rule is silent on an opaque value.
- **(b) Cross-file** (`src/utils/nest-modules.ts`): the package's `*.module.ts` files, parsed with the configured parser (falling back to `@typescript-eslint/parser`), cached per package root. Anything unreadable abstains; nothing throws.
- **(c) Type information** (`src/utils/type-info.ts`): used when `parserServices.program` exists, never required.

No verdict rests on a variable NAME. The last name heuristic in the plugin — no-algorithm-confusion's `/public/i`, `/publicKey/i`, `/getPublicKey/i`, `/jwks/i` — and the decode rule's `REQUEST_RECEIVER` / field-name grant exemption are gone. `npm run lint:name-inference` reports no new site.

**Recall locks.** Every fix also has invalid-side cases (each named "… keeps recall" or "… still reports"). They prove the rule still fires on the vulnerable shape after the FP fix. Examples:

- `FP-1 keeps recall: a const that lacks algorithms`
- `FP-5 keeps recall: destructuring an authority claim`
- `FP-6 keeps recall: header.alg without the option`
- `a jose builder held in a const with no expiry anywhere still reports`

**Existing tests changed** (each change is justified in a comment beside the test):

- **require-max-age:** `jwt.verify(token, secret, { clockTolerance: 30 })` moved from valid to invalid (FN-7). `clockTolerance` widens the expiry window, so accepting it as a max age certified a verify that caps nothing.
- **no-hardcoded-secret:** the inline `'-----BEGIN PUBLIC KEY-----…'` invalid case became `'-----BEGIN PRIVATE KEY-----…'`, which keeps the recall it was guarding. The public-key spelling moved to valid (FP-8).
- **no-decode-without-verify:** the corpus case `const { exp } = jwt.decode(token)` became `const { exp, sub } = …`. It had been reported only because destructuring was never followed, which was an implementation limit rather than a security judgement (FP-5).
- **coverage-dual-layer.test.ts:** the Layer-2 mock-context block covered the defensive guards inside `no-hardcoded-secret`'s private `resolveConstLiteralValue`. That function is deleted, so the block was removed with it.
- **utils.test.ts:** the `getOptionsArgument` cases were removed because the helper itself was removed. `resolveCallOptions` replaced it and is covered by the rule tests.

Zero-deferral pass (each flip is justified in a comment beside the test):

- **no-algorithm-confusion (FP-12):** eleven invalid cases that decided a key was public from its NAME (`publicKey`, `getPublicKey()`, `jwksKey`) moved to valid as `no evidence: …`; the mixed-family case stays invalid. Structural equivalents (`createPublicKey`, `importSPKI`, `createRemoteJWKSet`, a jwks-rsa signing key, a `.pub` read, a PEM const) were added as invalid. The audit-block case `a public key with HS* in a const options object` and the coverage-dual-layer loop-guard case flipped the same way, the latter with a PEM-keyed replacement.
- **require-algorithm-whitelist (FP-4 residual):** five invalid cases whose `this.<member>` had no evidence (a qualified-name type, a union type, an un-imported type, `this` outside a class, a computed `this[name]`) moved to valid as `no evidence: …`.
- **require-issued-at (FP-11b):** the three `noTimestamp: true` invalid cases moved to valid; no-timestamp-manipulation owns that report.
- **no-decode-without-verify (FN-8):** the five corpus cases exempted by field name (auth0 `extractActClaim`, Shopify `buildIdentityToken`, auth0 `warnIfNotCertificateBound`, auth0 `TokenSet.claims`, a `grant` parameter) moved to invalid as `no provenance: …`: none shows a back-channel response within its file.
- **coverage-dual-layer (value flow):** `let MUTABLE_SECRET = 'abc'` moved from valid to invalid — a `let` written once holds its initialiser; the reassigned spelling replaced it as valid. `{ ...claims, 'display-name': … }` with an unresolvable `claims` moved from valid to invalid (`wholeRecordSpread`, FN-6b).

## How the former deferrals were fixed

Each follows the owner's decision for it.

| Former deferral                                           | How it was fixed                                                                                                                                                                                                        |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FP-4 residual: untyped injected receivers                 | A `this.<member>` is a JWT client only on positive evidence the class gives: a type annotation resolving to a JWT import, an `@Inject(X)` of one, or an assignment from one. With none, the call is not treated as JWT. |
| FP-11 (b): `noTimestamp: true` reported twice             | require-issued-at no longer reports a literal `noTimestamp`; no-timestamp-manipulation owns `true`.                                                                                                                     |
| FP-12 (FP side): name heuristic in no-algorithm-confusion | The name patterns are removed. A key is public only on structural evidence (`isPublicKeySource`); the mixed-families signal stays.                                                                                      |
| FN-3 (b): NestJS module `signOptions.expiresIn`           | Read cross-file from the package's `*.module.ts` files; report only when every registration is readable and one lacks `expiresIn`.                                                                                      |
| FN-5 (b): unbounded `clockTolerance`                      | New option `maxClockToleranceSeconds` (default 300) on no-timestamp-manipulation; numeric values, consts and `+ - * /` are evaluated.                                                                                   |
| FN-6 (b): spread of a parameter / row into the payload    | Reported as whole-record exposure (CWE-200, `wholeRecordSpread`). With type information, only when the spread's type declares a sensitive field.                                                                        |
| FN-8: name-based grant-response exemption                 | Replaced by back-channel provenance (`src/utils/provenance.ts`): a `fetch()` body, an axios/got/ky/undici response, an openid-client grant (not `callbackParams`).                                                      |

## Preset changes

**`recommended`, `strict` and `legacy`: no change** in either pass. No rule was added, removed or re-levelled.

Behaviour changes that reach users through the existing presets:

- `no-hardcoded-secret` and `no-weak-secret` now set `skipTestFiles: true`, matching `require-expiration` and `no-decode-without-verify`. A fixture token signed with `'test-secret'` inside a test ships no credential. `no-hardcoded-secret` is the one rule in `legacy`, so legacy users also stop seeing test-file findings.
- New findings can appear in the default presets:
  - `ignoreExpiration: true` (`no-timestamp-manipulation`, recommended)
  - mixed HS\*/asymmetric `algorithms` lists (`no-algorithm-confusion`, recommended)
  - `||` / `??` fallback secrets and config-object secrets (`no-hardcoded-secret` / `no-weak-secret`, recommended)
  - `clockTolerance`-only verifies (`require-max-age`, strict)
  - jose builders without `setIssuedAt()` (`require-issued-at`, strict)

- Zero-deferral pass, new findings in the default presets:
  - a `clockTolerance` above 300 s (`no-timestamp-manipulation`, recommended; tune with `maxClockToleranceSeconds`)
  - an HMAC-only list against a structurally public key, and no longer against a key that is merely NAMED public (`no-algorithm-confusion`, recommended)
  - a whole record spread into the claims (`no-sensitive-payload`, recommended as `warn`)
  - a decode of a token whose back-channel origin is not visible in the file (`no-decode-without-verify`, recommended)
  - a NestJS `sign(payload)` whose `JwtModule` registration sets no `expiresIn` (`require-expiration`, recommended)
- Zero-deferral pass, findings that go away: `noTimestamp: true` from require-issued-at (strict), and every `this.<member>` call the class gives no JWT evidence for.

  All are intended. The changesets list them under "Upgrade notes".
