# FP/FN fixes — eslint-plugin-vercel-ai-security (2026-10-10)

This fixes the findings of the 2026-09-30 FP/FN review of v2.1.3: 26 false positives and 14 false negatives across 19 rules.

**Design constraint applied.** The fixes are AST-structural only. There is no taint or data-flow tracking, and nothing is guessed from a variable's name alone. The litmus test: rename every variable to `foo`/`bar`, and the rule must still fire on the bad shape and stay silent on the good one.

Three structural facts are used throughout:

- **Tool inputs are model output.** A tool's `execute` parameters are model-controlled by the SDK contract.
- **Request reads.** A value counts as user input when it is read from the request one declaration deep, in the same function: `const { x } = await req.json()`, `req.body.x`, `body.x` where `body = await req.json()`, or `searchParams.get(...)`. Here `req` must be a parameter of the enclosing function.
- **Name matching where kept.** Where name patterns survive, they are matched by whole camelCase segment (devkit `nameHasWord`), never by substring. They are used only to narrow evidence that has already been resolved, such as a sink or an SDK call.

**Test-first.** Each fix added a valid case (for an FP) or an invalid case (for an FN) to the rule's existing test file. I ran it and saw it fail before changing the rule. The exceptions were written together with their fix and not run against the unfixed rule: the `require-embedding-validation` audit cases, `a property read straight off the awaited call`, and `type assertions and non-null assertions do not hide the request`. So were cases added afterwards only to reach 100% branch coverage. The two locks fail on the unfixed code:

- `options-defaults.lock.test.ts`: all 18 affected rules match the forbidden pattern at `HEAD`.
- `recommended-preset.lock.test.ts`: the quickstart route showed 2 errors at `HEAD`.

**Existing tests that encoded an FP or FN were moved, not weakened.** Each moved case carries a `(Changed 2026-10-10)` or `(Moved 2026-10-10)` comment giving the reason.

## Zero-deferral pass (2026-10-11)

The owner relaxed the design constraint for this pass: bounded **intra-file value following** is allowed, along with optional type information. Deciding from variable names is still not allowed. Everything here is decided from AST shape, resolved bindings, resolved imports or declared types.

**What was added:**

- **`src/utils/flow.ts`** (`derivesFrom`) is a bounded same-file value follower (depth 16, 4,000 nodes per question, no binding re-entered on the current path). It follows a value through:
  - declarations, destructures and later assignments
  - `await`, `as`, `!`, `satisfies`, `?.`, ternaries, `??` / `||`, `+` and templates
  - member reads
  - array and string derivations (`.map`, `.filter`, `.join`, `.slice`, …) and value wrappers (`JSON.stringify`, `String`, `Number`, …)
  - the returns of same-file functions, with their parameters bound to the call's arguments
  - parameters, back to their same-file callers: direct calls, JSX component usages, and element callbacks (`xs.map(x => …)`)

  Rules supply the source and the barrier.

- **`src/utils/records.ts`** recognises a full database row by its client. The client is resolved through the import (`@prisma/client`, `pg`, `postgres`, `mysql2`, `knex`, `kysely`, `drizzle-orm*`, `@vercel/postgres`, `better-sqlite3`). A row with a column projection does not count.
- **`src/utils/type-info.ts`** is the optional type path. When `parserServices.program` exists, it returns the declared property names of a value's type. It returns `null` for `any` / `unknown`, or when no program exists, and callers then fall back to the structural check.
- **`src/utils/sdk.ts`** gains three helpers:
  - `isRequestDerived` now runs on `derivesFrom`.
  - `isSdkHookCall` matches `useChat` / `useCompletion` / `useObject` / `useAssistant`, resolved to the SDK.
  - `isSdkTypedParameter` matches a parameter whose type annotation names a type imported from `ai` / `@ai-sdk/*`, directly or through a same-file alias or interface.

## Preset changes (`recommended`)

The rule: a rule's level follows its own CVSS, `error` at 7.0 and above and `warn` below. Rules whose evidence is too weak for a default are `off` here and stay on in `strict`. `recommended-preset.lock.test.ts` pins the table, checks it against each rule's `meta.docs.cvss`, and lints three idiomatic AI SDK routes expecting 0 errors.

| Rule                           | Was   | Now       | Justification                                                                                                                                                                             |
| ------------------------------ | ----- | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| require-max-steps              | error | off       | The rule was inverted. It no longer reports the SDK's one-step default, only explicitly unbounded settings. That is a strict-mode hardening check. CVSS 6.5 would make it `warn` at most. |
| require-abort-signal           | error | off       | Its own CVSS is 4.0 (LOW). It fired on the AI SDK quickstart route and duplicated require-request-timeout on the same call.                                                               |
| require-request-timeout        | warn  | off       | CVSS 5. It fired on the quickstart, duplicated abort-signal, and reported option objects it had not inspected.                                                                            |
| no-training-data-exposure      | warn  | off       | Matching flag names and URL segments has no link to an actual provider data-sharing setting. A clean signal needs provider configuration knowledge.                                       |
| require-output-filtering       | warn  | off       | It cannot tell a sensitive data source from a benign one without types. Even after the fix it is a review prompt, not a finding.                                                          |
| require-max-tokens             | error | warn      | CVSS 6.5. A provider-side output cap already exists. This is defensible hardening, not an error.                                                                                          |
| require-tool-schema            | error | error     | CVSS 7.5: consistent.                                                                                                                                                                     |
| require-tool-confirmation      | error | error     | CVSS 7.0: consistent.                                                                                                                                                                     |
| require-rag-content-validation | warn  | warn      | CVSS 6.0: consistent.                                                                                                                                                                     |
| All other rules                | —     | unchanged | `error` at CVSS 7.5–9.8. `off` already for error-handling, audit-logging, embedding-validation and output-validation.                                                                     |

Net effect: `recommended` goes from 11 errors + 4 warnings to 8 errors + 2 warnings. The AI SDK v5 quickstart route goes from 2 errors + 1 warning to 0 errors (1 `require-max-tokens` warning).
