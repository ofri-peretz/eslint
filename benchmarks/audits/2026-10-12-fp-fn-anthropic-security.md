# FP/FN audit: eslint-plugin-anthropic-security (2026-10-12)

The audit ran against the published 0.3.4, which matched `main`. It found 3 false-positive classes and 3 false-negative classes across the 3 rules. All are fixed. After the fixes, the real-code scan shows only true positives.

**Where the fixes live.** The three rules are instantiations of devkit factories (`createSdkApiKeyRule`, `createBrowserEscapeHatchRule`, `createSystemPromptInjectionRule`), and only this plugin, `openai-security` and `gemini-security` use those factories. The fixes are therefore in `packages/eslint-devkit/src/rule-creation/` (`sdk-flow.ts` is new; `sdk-api-key-rule.ts`, `browser-escape-hatch-rule.ts`, `system-prompt-injection-rule.ts` and `module-evidence.ts` changed), plus the plugin's rule configs. **The devkit needs a release alongside the 1.0.0.**

**Design constraint.** Every verdict comes from AST structure, from the scope manager, and from bounded same-file value following (8 hops; it abstains on a reassigned `let`, a parameter or an import). SDK identity is resolved through the import or `require()`, never through a local name. Literal _values_ are judged by their shape: a key must look like a generated token. Rename litmus: each rule's tests include a case with every identifier renamed, and it still reports.

## Method

- **Synthetic.** 15 snippet files in the published version's scratch install, covering `messages.create` / `stream`, the cache-control system array, tools, Bedrock / Vertex / Foundry clients, CJS, dynamic import, subclasses, wrappers and options in variables.
- **Real code.** Every file that imports `@anthropic-ai/*` was linted with all 3 rules.

**Test-first.** I copied each new test file into a scratch tree that holds the `HEAD` sources (`git archive HEAD`) and ran it there. 34 of the 42 `FP:`/`FN:` cases in that run failed, as expected. The Message Batches case was added afterwards; I re-ran it on `HEAD` the same way, and it fails there too. The other 8 passed on `HEAD`, because the old any-call matching happened to catch them (subclass, `super()`, wrapper, `withOptions`, namespace and lazy imports, and a dynamic system-array block). They are renamed `guard: …`, and they pin the new binding resolution so it does not lose those shapes.

**Existing tests moved** (each with a comment in the test file):

- 5 invalid cases used stand-in keys (`'sk-ant-x'`, `'tok-live-123'`). They moved to valid as `(was invalid) …`, and each mechanism (authToken, a quoted key, `require()`, a safe apiKey beside an authToken) is re-pinned with a key-shaped value.
- 2 invalid cases used a callee the SDK does not bind (`createAnthropic`, and an `Anthropic` that nothing imports). They moved to valid.
- The module-gate lock's sweep over load forms now probes with `no-untrusted-content-in-prompt`, which needs only the gate. A re-export binds no local name, so the key rule cannot show the gate opening through it. The positive control still uses the key rule, with a key-shaped value.
