# Benchmark raw-results extraction plan

> **Status:** Phase 1 — plan only. No application code changed. No behaviour changed.
> **Author:** Base44 (agent), 2026-08-22
> **Brief:** Extract `benchmarks/results/` (66 MB, 96 tracked files) into a dedicated research repo without silently disabling any rigor guardrail.

---

## 0. The two directories — which is which

This repo has two benchmark-output directories with confusingly similar names. They are fundamentally different things:

| | `benchmarks/results/` | `benchmark-results/` |
| :--- | :--- | :--- |
| **Size** | 66 MB across 96 tracked files | 2.1 MB across 185 tracked files |
| **Largest file** | 52 MB (`ilb-flagship/2026-05-11.json`) | ~50 KB (typical report) |
| **What it holds** | **Raw** per-suite dated JSON snapshots — the full per-fixture, per-run output of each benchmark suite. Append-only history. | **Derived** live state — scorecards, reports, baselines, history.ndjson. Regenerated by scripts on every run. |
| **Who writes it** | Suite runners (`benchmarks/suites/*/run.ts`) at the end of each run. | Scripts (`scripts/ilb-*.ts`) that read the raw dir, compute aggregates, and emit markdown/JSON. |
| **Who reads it** | Suite runners (for baselines/regression), the docs app (scorecard page), CI gates (validate-results, per-rule-budget), the scorecard emitter. | Lock tests, CI workflows (for committing derived state), the docs app (indirectly via scorecard page links). |
| **Regenerable?** | **No** — raw results are evidence of a specific run at a specific toolchain. Historical files cannot be reproduced (toolchain unknown, corpus may have drifted). | **Yes** — every file is regenerable from a single npm script (`benchmark-results/README.md` says so explicitly). |
| **Grows every run?** | **Yes** — every benchmark run adds new dated files. This is the bloat source. | **No** — derived files are overwritten, not appended (except `history.ndjson`). |
| **In `.gitignore`?** | No (tracked). One sub-path is gitignored: `benchmarks/results/ilb-oxlint-parity/.parity.oxlintrc.json` (`.gitignore:147`). (`harvested-fixtures/` is gitignored at `.gitignore:146` but lives under `benchmarks/suites/`, not `benchmarks/results/`.) | No (tracked). |

**The extraction target is `benchmarks/results/` only.** `benchmark-results/` stays — it's small, derived, and every file in it is regenerable from a script. Moving it would break lock tests and CI workflows that read derived state, with no size benefit.

## 4. Ordered migration steps

Each step is independently revertible. Steps must land in this order — each depends on the previous.

### Step 0 — Fix the vacuous-pass gate (Phase 2 of the brief, can land first)

**This is the one slice the brief authorises for Phase 2.** It's worth doing whether or not the migration ever happens.

- Make `ilb-validate-results` fail loudly on an empty or missing results directory.
- Add a lock test that fails if someone reintroduces the vacuous pass.
- **Verification:** `npm run ilb:validate-results` with an empty/missing dir → `exit 1`. Lock test fails on unfixed code, passes on fix.
- **Revertible:** revert the commit. No data movement.
- **Must land before:** Step 1 (so the gate is already loud when the dir shrinks).

### Step 1 — Create the research repo and seed it

- Create `ofri-peretz/eslint-benchmark-results` (or similar name — **open question O1**).
- Push the current `benchmarks/results/` contents to it as the initial commit.
- Verify the research repo has all 96 files, 66 MB.
- **Verification:** `git clone` the research repo, `diff -r` against `benchmarks/results/` → identical.
- **Revertible:** delete the research repo. This repo is untouched.
- **Must land before:** Step 2 (consumers need a target to fetch from).

### How this repo learns that the research repo's gate failed

If the `ilb:validate-results` gate moves to the research repo (an alternative to the fetch approach), this repo needs a way to know when it fails. Options:

- **B) Cross-repo gate:** The research repo runs its own `ilb:validate-results` and this repo's CI checks the research repo's latest CI status via `gh api`. More complex, adds a network dependency to the gate.

**Recommendation: A (fetch approach).** It keeps the gate in this repo, preserves the existing `quality` composite, and avoids cross-repo orchestration. The fetch is a `git clone --depth 1` of the research repo into a gitignored cache — fast, deterministic, and cached by CI.

## 6. Git history decision

### The problem

`git rm -r benchmarks/results/` removes the files from future commits but the 66 MB of blobs (including the 52 MB `2026-05-11.json`) stays in history forever. Every clone still downloads it.

### Options

| Option | Cost | Blast radius | Recommendation |
| :--- | :--- | :--- | :--- |
| **A) Plain `git rm` (no rewrite)** | Zero. The 66 MB stays in history. | None — all clones and PRs continue working. | **If the repo is young and clones are rare:** acceptable. The 66 MB is a one-time cost. |
| **B) History rewrite (`git filter-repo`)** | Moderate. Requires force-push to `main`, breaks all open PRs, every contributor must re-clone. | **High.** Every existing clone becomes invalid. Every open PR must rebase. Every fork must be updated. | **If the repo is established with contributors and forks:** do it, but carefully. |

### Recommendation: **A (plain `git rm`), unless Ofri decides otherwise.**

Reasoning:

1. The repo has branch protection, CODEOWNERS, and an active PR flow. A force-push to `main` would break every open PR and every contributor's local clone.
2. The 66 MB is a one-time clone cost. After the `git rm`, new clones get the 66 MB from history but never grow further (the raw dir is gitignored).
3. GitHub's `git clone` uses delta compression, so the real transfer cost is less than 66 MB.
4. If the history weight becomes a real problem later, a rewrite can be done as a separate, planned operation with coordination.

### What I'd need from Ofri to do a rewrite (option B)

- Confirmation that all open PRs can be rebased (or will be closed).
- A communication plan for contributors (they must re-clone).
- A maintenance window (force-push to `main` blocks all PRs during the rewrite).
- Confirmation that no downstream forks need to be preserved.
