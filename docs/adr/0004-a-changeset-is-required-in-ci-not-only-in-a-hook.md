# ADR 0004 — A changeset is required in CI, not only in a hook

- **Status:** accepted
- **Date:** 2026-09-01
- **Deciders:** @ofri-peretz

## Context

Releases are changeset-driven. A package source change that merges **without** a
changeset never gets a version bump, so `release.yml`'s `detect` compares local
`package.json` against npm, finds them equal, and publishes nothing — no failing
step, no signal.

The rule already existed: `lefthook.yml` runs `check-changeset-coverage.ts` on
pre-commit. But a local hook is advisory by construction. `--no-verify` and
`LEFTHOOK_EXCLUDE` both skip it, and agents committing in sandboxes skip it
routinely — every commit in this session did. Nothing in `quality.yml` or
`quality-full.yml` re-asserted it.

Making it a merge gate first required making it **accurate**. The rule matched
`packages/<name>/package.json` as a whole file, so a repo-wide `tsc` → `tsgo`
edit to `scripts.typecheck` flagged **33 packages** as consumer-visible — none
of which a consumer can observe. A gate that fires on script hygiene is one
people learn to bypass, which is how it ended up enforced nowhere.

## Decision

Run `check-changeset-coverage.ts --strict` in CI, in the `publish-metadata` job
(which already pays for an install), with two refinements:

1. **`package.json` is judged per field.** `scripts` and `devDependencies` are
   build-time; `exports`, `peerDependencies`, `version`, `engines`, `os`, `cpu`,
   `libc`, `bundleDependencies`, `imports` and `private` are shippable.
2. **The Version PR is exempt.** `changeset-release/main` is generated by the
   changesets action: it *consumes* changesets by deleting them and bumps every
   version, presenting the exact shape the gate rejects while being the only PR
   whose purpose is to publish.

## Consequences

- Merging a package change now implies a changeset exists, so the release path
  is reachable by construction.
- Without exemption (2), the gate blocks the release mechanism itself — #787
  failed naming 21 packages, and no version could ship. Discovered the hard
  way, hours after the gate landed.
- The `skip-changeset` label remains the escape hatch for genuinely
  internal-only work, where a human states the reason.
- Both refinements are locked, and both locks are sabotage-proven: reverting
  the field rule fails exactly the two false-positive tests, and dropping the
  Version PR guard fails with the consequence named.

## Alternatives considered

**Leave it advisory.** The script's own docstring argues for this: "a missing
changeset is a judgement call the author makes, not a correctness failure a
machine can decide". That reasoning is about blocking a *push*. Blocking a
*merge* is a different question, and the maintainer's requirement — every merge
that changes a package releases it — cannot hold while the rule is skippable.

**Derive the bump from the commit type** (feat→minor, fix→patch, `!`→major).
Still open. It would remove the remaining human judgement, and is the natural
successor to this decision rather than a competitor.
