# Intent — the docs pages people land on fetch GitHub before they render

> Stage 1 artifact of the AI-native SDLC. Opened from PostHog: the highest-traffic
> docs page is also the slowest and the highest-bouncing, and the three facts have
> one cause.

**Status:** draft · **Opened:** 2026-09-02 · **Owner:** @ofri-peretz

---

## What is wanted

The pages readers arrive on render from data already in the build, not from a
network round trip taken while the reader waits.

## Why now

Three independent 90-day measurements converge on the same pages.

Traffic and bounce (`query-web-stats`, `eslint.interlace.tools`):

| Page | Visitors | Bounce |
| :--- | ---: | ---: |
| `/docs/security/plugin-vercel-ai-security` | 191 | 96.6% |
| `/` | 181 | 59% |
| `/docs/quality/…/rules/no-unreadable-iife` | 149 | 100% |
| `/docs/getting-started/concepts` | 96 | 100% |

LCP p75 (`query-web-vitals`, same window):

| Page | LCP p75 | Band |
| :--- | ---: | :--- |
| `/docs/security/plugin-secure-coding/rules` | 7878 ms | poor |
| `/docs/security/plugin-vercel-ai-security` | 6710 ms | poor |
| most rule pages | 80–190 ms | good |

The top-traffic page is the second-slowest on the site, at 2.7x the "good"
threshold. Rule pages — static MDX — are 80–190 ms, so this is not site-wide. It
is two components:

- **`RemoteReadme`** (30 plugin index pages) fetches
  `raw.githubusercontent.com/.../README.md` at request time and compiles it to
  MDX before the page can paint. One blocking round trip.
- **`RulesTable`** (`/rules` listings) does the same, then calls
  `fetchRuleDescriptions`, which fetches each rule's doc individually —
  **78 round trips** for `secure-coding`.

`rules-table.tsx` already has `readLocalReadme()`, reading from the monorepo
checkout. It is disabled in production by one line:

```ts
if (process.env.NODE_ENV === 'production') return null;
```

`remote-readme.tsx` has no local path at all.

A cache also exists — `apps/docs/src/data/plugin-rules/` — generated by a sync
script. **Nothing reads it.** It holds 9 of 30 plugins and was last synced
2026-08-25. The fix was started and abandoned.

The bounce was previously read as a content problem. A reader arriving from
search at a 6.7-second page mostly leaves before it renders, so content work on
that page would have been spent on an audience that never saw it.

## Affected users and systems

`apps/docs/src/components/docs/remote-readme.tsx`, `rules-table.tsx`, the 30
plugin index pages, every `/rules` listing, and `apps/docs/src/data/plugin-rules/`.
Downstream: organic search, which is how these pages are reached — `$referrer` on
the sampled sessions is Google.

## Constraints

- **Docs does not depend on the plugin packages.** `apps/docs/package.json` lists
  `@interlace/benchmarks` and `@interlace/ui` only, so a README-only change does
  not make docs turbo-affected and does not redeploy it. Any move to build-time
  data must say how a changed README reaches the site, or the pages go stale
  instead of slow.
- Do not remove the network fallback. A missing local file must degrade to
  today's behaviour, not to an empty page.
- The freshness claim is printed on the page — "fetched directly from README.md
  on GitHub and cached for 1 hour". If that stops being true, the copy changes
  with it.

## Success criteria

- `/docs/security/plugin-vercel-ai-security` LCP p75 is inside the `good` band
  (< 2500 ms), measured over a window after the change rather than predicted.
- No `/rules` page makes a per-rule network request at request time.
- The `plugin-rules` cache is either read by the code or deleted — not left as a
  third state that looks like coverage.
- A budget check fails if an index page regresses past the band.

## Open questions

- Build-time read from the checkout, or a committed JSON cache refreshed on a
  cron? The second survives a runtime with no monorepo present; the first is
  simpler with no staleness window of its own.
- If READMEs move to build time, does `packages/*/README.md` join the docs turbo
  inputs, or does a scheduled redeploy carry freshness?
- Is `fetchRuleDescriptions` needed at all, given `sync-rules-docs.ts` already
  generates rule data locally?
